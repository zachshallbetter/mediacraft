# MediaCraft — Product and System Contract

**Contract ID:** `mediacraft.product-system`  
**Version:** `0.1.0-draft`  
**Status:** Proposed; not an assertion of implementation or conformance  
**Scope:** MediaCraft desktop application, its local services, and its integration boundaries with Craft applications  
**Companion documents:** `INTERFACE.md`, `MEDIA_INFRASTRUCTURE_SPEC.md`, `DEFINITION.md`, `FEATURES.md`, `LAB_NOTES.md`

## 1. Purpose and interpretation

MediaCraft is a filesystem-native workspace for discovering, organizing, inspecting, transforming, validating, and delivering media assets. It combines asset management with media processing, but does not replace FilmCraft, PhotoCraft, SoundCraft, or EffectCraft as creative editors.

**MUST**, **MUST NOT**, **SHOULD**, and **MAY** denote normative requirements, recommendations, and optional behavior. A feature is not considered delivered because it appears in this contract: implementation requires observable acceptance evidence. Versioned contracts are subject to review and adoption; this draft does not bind `craft-libs` maintainers or other Craft applications.

## 2. System boundary

| Domain | Owns | Does not own |
|---|---|---|
| Asset Engine | Filesystem observations, catalog/index, thumbnails, collections, metadata projections, offline references, asset/derivative relationships | The original file bytes as a proprietary library |
| Media Engine | Probing, stream/capability descriptions, transformation planning and execution, technical validation | Creative timelines, DAW sessions, image editing documents |
| Workflow Engine | Persistent jobs, dependencies, ingest, watch rules, recipes, processing history and receipts | Other apps' editor-specific workflows |
| Desktop UI | Library, Inspect, Process, Queue; contextual Collections and Automations | A permanently mandatory four-panel encoder layout |
| Shared Craft candidates | Narrow reusable codec/container/media contracts proven with consumers | Automatic migration of app-specific catalogs, UI, or unqualified codecs |

The filesystem remains authoritative for file contents and location. The catalog is an optional, reconstructable projection. Core browsing and processing MUST remain usable without a cloud account or optional ML features.

## 3. Core invariants

1. **Source preservation.** A transformation MUST NOT overwrite or silently mutate source media. Any destructive file operation MUST require explicit user intent, preflight, and an auditable result.
2. **Truthful capability disclosure.** Support MUST be reported per operation, format, codec, container, profile, platform, and installed implementation. A known format is not automatically a supported encoder.
3. **Typed uncertainty.** Missing, inferred, conflicting, and verified metadata MUST be distinguishable. Unknown color information MUST NOT be presented as confirmed Rec.709 or another standard.
4. **Stable asset reference.** Catalog asset identity MUST NOT be defined solely by path or filename. File instances and content observations MUST be modeled separately.
5. **Non-destructive derivatives.** Outputs MUST have a relationship to their source observation/version, operation, settings/recipe version, and execution receipt when generated by MediaCraft.
6. **Honest completion.** A successful process exit MUST NOT be represented as a verified deliverable unless the configured verification checks pass. Verification outcomes are `accepted`, `warning`, `rejected`, or `not_run`.
7. **Recoverable execution.** Persisted jobs MUST survive application restart. An interrupted job MUST NOT be marked completed without a valid output receipt; resumability is capability-dependent.
8. **Safe automation.** Watch-folder jobs MUST avoid processing incomplete inputs and MUST define duplicate handling, idempotency, permissions, and failure reporting.
9. **Transparent planning.** MediaCraft SHOULD prefer stream copy/remux when technically legal and sufficient. It MUST disclose when a requested result requires lossy re-encoding or cannot be performed exactly.
10. **Bounded operations.** Background indexing, previews, and processing MUST support cancellation and enforce configurable resource bounds.

## 4. Canonical domain records (conceptual contracts)

These are logical schemas, not a promise of a specific database, Rust type, or public wire format. Public serialization MUST be explicitly versioned before adoption.

### 4.1 Asset and file instance

```yaml
asset:
  asset_id: opaque-stable-id
  asset_kind: video | audio | image | sequence | project | unknown
  display_name: string
  observations: [file_instance_id]
  metadata: [metadata_fact]
  relationships: [relationship_id]

file_instance:
  file_instance_id: opaque-id
  asset_id: opaque-stable-id
  location: uri-or-path
  availability: online | offline | missing | unknown
  size_bytes: integer-or-null
  observed_mtime: timestamp-or-null
  fingerprint: {algorithm: string, value: string, confidence: verified | provisional | unavailable}
  observed_at: timestamp

metadata_fact:
  key: namespaced-key
  value: typed-value
  provenance: embedded | sidecar | probe | user | inferred
  confidence: verified | reported | inferred | unknown
  observed_at: timestamp
```

An asset can have multiple observed instances. Relinking MUST preserve ambiguity when identity cannot be established. Matching by filename alone MUST NOT silently merge two assets.

### 4.2 Stream and capability

```yaml
stream:
  stream_id: opaque-id
  media_kind: video | audio | subtitle | data
  codec: string-or-unknown
  time_base: rational-or-unknown
  duration: rational-or-unknown
  properties: typed-map
  evidence: probe-reference

capability:
  operation: probe | decode | encode | remux | extract | transform | verify | preview
  input_constraints: typed-map
  output_constraints: typed-map
  implementation: name-and-version
  availability: available | unavailable | conditional | unknown
  limitations: [typed-reason]
```

A capability query MUST reflect the actual runtime environment and MUST return reasons for conditional or unavailable operations. Codec names, container names, and delivery profiles MUST remain distinct concepts.

### 4.3 Transformation request, plan, and job

```yaml
request:
  request_id: opaque-id
  source_asset_id: opaque-stable-id
  source_observation: file-instance-and-fingerprint-reference
  intent: convert | optimize | extract | proxy | prepare | analyze | remux | ingest
  output_target: uri-or-path
  recipe: {id: string, version: string, parameters: typed-map}
  delivery_contract: optional-versioned-constraint-set
  overwrite_policy: deny | explicit-replace

plan:
  plan_id: opaque-id
  request_id: opaque-id
  steps: [probe, copy-or-remux-or-decode-filter-encode, package, verify]
  feasibility: feasible | conditional | infeasible
  reasons: [typed-reason]
  estimates: optional-nonbinding-values

job:
  job_id: opaque-id
  plan_id: opaque-id
  state: queued | running | paused | completed | failed | cancelled
  progress: optional-stage-and-fraction
  attempts: integer
  events: append-only-event-references
  result: optional-output-and-receipt-references
```

A request can generate multiple outputs and dependency-linked jobs. A dry run MUST be available before any operation that can replace, move, or rename files.

### 4.4 Derivative and verification receipt

```yaml
derivative:
  relationship_id: opaque-id
  source_asset_id: opaque-stable-id
  source_observation: immutable-reference
  output_asset_id: opaque-stable-id
  relation: proxy | delivery | extraction | thumbnail | version | other
  recipe_id: string
  recipe_version: string
  execution_receipt_id: opaque-id
  freshness: current | stale | unknown

receipt:
  receipt_id: opaque-id
  job_id: opaque-id
  source_fingerprint: algorithm-and-value-or-unavailable
  output_fingerprint: algorithm-and-value-or-unavailable
  implementation_versions: typed-map
  requested_constraints: versioned-reference-or-null
  checks: [{check_id: string, result: pass | warn | fail | not_run, evidence: reference}]
  verdict: accepted | warning | rejected | not_run
  completed_at: timestamp
```

A receipt MUST distinguish verified measurements from estimates. A stale source observation MUST cause derivative freshness to be reevaluated; it MUST NOT silently remain `current`.

## 5. User-visible behavior contract

| Surface | Required baseline behavior | Failure/edge behavior |
|---|---|---|
| Library | Open local folders, enumerate supported assets, thumbnails or typed placeholders, sorting, selection, search/filter | Unreadable files are shown with an error; large scans can be cancelled |
| Inspect | Preview when supported; report container, streams, dimensions, duration, audio and color evidence | Unknown or unsupported properties are labeled, not invented |
| Process | Intent-first actions; source-aware output options; expert settings available | Incompatible targets explain why; no silent format substitutions |
| Queue | Durable jobs, progress, pause/cancel, retry, logs, outputs, receipt status | Interrupted/failed jobs remain inspectable; no false success |
| Collections | User collections and saved filters refer to indexed assets without copying originals | Offline items remain identifiable; broken references are visible |
| Automations | Explicit watched locations, rules, recipes and execution history | Partially written or duplicate arrivals are handled predictably |

**Visual/UI direction:** Align with Craft application styling: restrained dark professional workspace, consistent controls and typography, library-first launch, compact navigation, central media grid, contextual inspector/process panel, collapsible activity queue. The engraved octopus on a vermilion-red rounded square is the proposed MediaCraft icon identity; brand approval and exact color token remain design decisions. The supplied mockups are visual references, not implemented behavior or pixel-exact UI specifications.

## 6. Ingest and filesystem mutation contract

Verified ingest is distinct from ordinary import or indexing.

- Ingest MUST specify source, one or more destinations, verification algorithm, collision behavior, and source-retention policy before copying.
- Each destination MUST be independently verified against the selected source content before the operation is reported as verified.
- A copy error MUST preserve the original and MUST produce a per-destination failure record.
- MediaCraft MUST NOT delete or format camera media automatically as a consequence of successful ingest.
- Move/rename MUST preflight collisions, report partial failures, and provide rollback/undo where feasible; unsupported undo MUST be disclosed beforehand.
- Watch folders MUST define file-stability/completion checks and avoid duplicate work after restarts.

## 7. Processing and delivery contract

The execution sequence is **Inspect → Plan → Execute → Verify → Deliver**.

- The planner MUST distinguish stream copy, remux, and re-encode. A requested frame-exact trim MUST NOT be promised when only keyframe-boundary copy is feasible.
- Source timestamps, time bases, audio sample counts, timecode, stream dispositions, and color signaling MUST be preserved or deliberately transformed according to the selected operation; unsupported preservation MUST be disclosed.
- Hardware acceleration MUST be discovered per stage and device, with recorded software fallback where available. Equivalent settings do not imply bit-identical outputs across encoders.
- A preset stores parameters. A **delivery contract** stores testable requirements. Passing a preset alone does not establish delivery compliance.
- Verification MUST declare its scope (e.g., structural probe only versus full decode, stream timing, loudness, or visual quality). A limited check MUST NOT imply comprehensive quality assurance.
- For AAC/M4A, encoder delay, end padding, edit lists, and playback timing MUST be tested against actual fixtures; 1024-sample priming MUST NOT be assumed universally.
- `moov` before `mdat` MAY be used as a structural faststart check, but MUST NOT alone establish real-world seekability.

## 8. Integration contract with Craft applications

Craft integrations SHOULD use narrow, versioned requests and receipts, not direct coupling to MediaCraft UI or catalog internals. A submitting app retains ownership of its project document, timeline/session state, export intent, and application-specific semantics.

Minimum proposed interface families:

| Interface | Request | Result |
|---|---|---|
| `media.capabilities` | Operation and constraints | Actual available implementations, limitations, reasons |
| `media.probe` | Source reference | Stream/metadata facts with provenance |
| `media.plan` | Source, intent, constraints | Feasibility, proposed steps, warnings |
| `media.jobs.submit` | Versioned request/plan | Durable job ID |
| `media.jobs.get` | Job ID | State, progress, typed errors, outputs |
| `media.jobs.control` | Job ID + permitted action | Acknowledged transition or rejection reason |
| `media.receipts.get` | Receipt ID | Validation results and reproducibility evidence |

These are **proposed semantic interfaces**, not existing API endpoints. Transport (local IPC, CLI/JSON, Rust API, MCP), authentication, and schemas require separate adoption. Shared `craft-libs` extraction requires a proven second consumer, preserved application behavior, tests, and maintainer approval. No bulk crate extraction is authorized by this document.

## 9. Security, privacy, and resource limits

- Filesystem access MUST be limited to user-authorized paths and OS-granted permissions; search indexing MUST honor exclusions.
- Remote upload, cloud inference, and external model calls MUST be opt-in and identify data leaving the device.
- Metadata, filenames, embedded paths, and logs MAY contain sensitive information; exported reports MUST support redaction.
- Processing MUST handle untrusted media as potentially malformed input, with bounded memory, timeouts/cancellation, and isolated subprocesses where appropriate.
- Jobs MUST NOT execute arbitrary shell commands embedded in media metadata or filenames.
- Logs MUST NOT record credentials or tokens; destructive and remote actions MUST require explicit authorization.

## 10. Release gates and evidence

| Gate | Target | Minimum acceptance evidence |
|---|---|---|
| G0 | Contract and narrow shared-media proof | Versioned contracts, golden vectors, container/timing tests, independently verified second consumer |
| G1 | Browse and index | Mixed-media fixtures, incremental rescan, bounded resources, cancellation, offline/relink tests |
| G2 | Preview, inspect, search | Representative audio/video/image fixtures, truthful unknowns, responsiveness and error cases |
| G3 | Convert and durable queue | Stream-copy/transcode cases, persistent restart, pause/cancel/retry, source immutability, output receipts |
| G4 | Collections and safe batch operations | Saved predicates, collision tests, move/rename recovery, metadata provenance |
| G5 | Derivative graph and delivery checks | Multi-output relationships, stale-source detection, intentionally invalid outputs rejected |
| G6 | Verified ingest and automation | Multi-destination hash tests, interrupted copy, partially written files, idempotent watch rules |
| G7 | Advanced discovery and enhancement | Explicit privacy/capability gates, quality fixtures, reproducible model/runtime records |

A gate is **passed** only with pinned code revision, fixture identifiers, commands, test results, and a reviewable receipt. Product mockups, capability inventories, and exploratory lab notes are not sufficient evidence of a passed gate.

## 11. Exclusions and deferred decisions

Not part of the baseline contract: full nonlinear video editing, DAW features, compositing, mandatory cloud asset management, universal codec support without licensing qualification, guaranteed frame-exact lossless cuts, guaranteed recovery of corrupt media, unqualified AI enhancement, or distributed encoding.

Decisions still required before implementation: persistent catalog format and identity reconciliation; metadata sidecar/write policy; public transport and versioning; exact supported format matrix by platform; verification profiles; safe automation permissions; cache eviction and quotas; UI design tokens and icon finalization.

## 12. Change control

Any change to asset identity, source preservation, job states, verification verdicts, integration payloads, or receipt semantics requires a versioned contract revision and compatibility assessment. Implementations MAY extend internal fields but MUST NOT silently change the meaning of published fields. Breaking external API changes require an explicit migration path.
